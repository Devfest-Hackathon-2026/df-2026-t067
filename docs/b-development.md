# B担当：旅行者の地図・問題閲覧

この文書は、旅行者向けT01/T02と挑戦開始の入口を担当するBの作業範囲を整理する。ここに記した「提案」「未決」は、実装済み仕様や確定したAPI契約ではない。共通契約の変更が必要な項目はA/Cと確認してから決める。

## 現在の実装

- [旅行者向け画面](screens.md)のT01/T02の一部として、全国地形の静的SVGプレビューと拡大縮小、公開APIから選んだ問題の詳細開閉を実装済み。APIモードでは固定デモマーカーを表示しない。
- Googleログインは既存のT03実装へつながる。未ログインでも問題を見られ、選択中の問題を保ったままログインを開始できる。
- 地図の出典・限界と、現在のUIの動作は[旅行者向けUI](traveler-ui.md)に記載済み。APIモードでは静的な架空マーカーを非表示にし、問題の位置を表しているように見せない。
- API共通型の`PublicArea` / `PublicQuest`を使い、起動時に公開問題一覧をページ単位で取得し、選択したIDの詳細と対応地域名を取得する（[共通API初期実装](api.md#8-最初の共通api実装)、[ローカルAPI](api.md#9-ローカルapiの土台)）。閲覧は未認証で行う。取得失敗時は再試行を表示し、固定デモへ切り替えない。サーバー応答のデータ自体は架空のデモ。
- T02の表示は`QuestDetails`へ分離し、共通`PublicQuest`と表示用の地域名を受け取る。現行の架空デモにも架空ID `demo-harbor-clock` と版1を設定した。実APIの問題ID・版とは混ぜない。`App`では`quest`と`areaLabel` propsで別の共通DTOを注入できる。
- `App`の`onStartChallenge`は、T04等の受け手へ `{ questId, expectedVersion }` を渡す任意の境界。既存の`createChallenge`入力型から型を導出している。ログイン前にID・版を保持し、ログイン成功状態を認証スナップショットで確認してから、問題詳細が開いたままでID・版も同じ場合だけ通知する。取消・認証失敗・選択変更・詳細を閉じた場合は渡さない。
- Google認証が設定済みなら、未ログイン状態でも挑戦ボタンからGoogleログインは従来通り可能。認証設定がない場合も閲覧はできるが、ログインボタンは無効になる。最新mainのC担当による端末内の撮影・写真確認を維持する。APIモードの撮影入口は、A担当のサーバーuid確認が成功した後に利用できる。ログイン成功や端末内プレビューを、サーバーでの挑戦登録・判定成功とは表示しない。
- 現在の開発用起動画面では、既定の撮影入口にmainの`ChallengeCapture`を使い、問題ID・版を挑戦開始APIへ渡す。`onStartChallenge`はカスタム受け渡し先を注入する境界として維持する。接続時は`<App onStartChallenge={(input) => api.createChallenge(input)} />`のように既存API入力を渡す境界となる。カスタム受け渡しは自動テストで確認し、既定の挑戦開始・撮影経路もmainの回帰テストで確認する。

- 地域選択（全国／公開地域）から、その地域の公開問題へサーバー側で絞り込める。地域名と公開問題件数を表示し、地域変更時は問題選択を戻して再取得する。0件・通信失敗・再試行は区別する。地域・一覧・詳細を取得する一連の処理は10秒で打ち切り、応答が停止しても再試行へ戻す。時間切れ後の遅い応答は表示せず、成功・切替・破棄時には待ち切りタイマーも解除する。地域選択は問題が0件でも操作できる。静的地図のマーカーとは結び付けない。

## 未実装・阻害要因


- `PublicQuest`には`hintCount`と任意の`optionalHintImage`があるが、段階ヒント本文を取得するAPI・共通型・サーバー実装はない。現在のデモ文面は段階ヒントの実データではない。ヒント本文を作り足したり、新APIをBだけで定義したりしない。
- 選択中の問題ID・版を既存の`createChallenge({ questId, expectedVersion })`へ渡し、最新mainのサーバー側の挑戦開始とCのGPS付き撮影・写真確認を維持する。画面からの写真・GPS送信は未接続。
- 静的SVGは実地図ではなく、公開探索エリアの形状・代表点を描画しない。`server`の架空デモ座標は日本地図上の実地域を表さないため、そのまま日本地図へ投影しない。有料・課金を伴う地図サービスの有効化は別途承認が必要。

## 実装の構造と接続方法

1. [`QuestDetails`](../src/features/quests/QuestDetails.tsx)は共通`PublicQuest`と`areaLabel`を受け取って表示する。認証SDKやAPIを呼ばず、閲覧に認証を要求しない。挑戦ボタンが押された時点の`quest.questId`と`quest.version`から入力を作る。
2. [`App`](../src/App.tsx)はGoogleログインと受け渡しを調整する。ログイン済みなら直接通知し、未ログインならポップアップの完了と認証状態の確認後に通知する。認証状態の通知が遅れた場合は最大5秒待ち、確認できなければ閲覧を維持して再操作を案内する。
3. ログイン待機中に別ID・版へ変更した場合、詳細を閉じた場合、画面を破棄した場合、認証クライアントを差し替えた場合は古い処理から通知しない。処理中は重複実行を抑止する。受け渡し先がPromiseを返す場合は完了まで待つ。

接続例（`selectedQuest`は既存の`PublicQuest`。`startChallenge`はA/C側が用意する処理）：

```tsx
<App
  quest={selectedQuest}
  areaLabel="公開探索地域の名前"
  onStartChallenge={async ({ questId, expectedVersion }) => {
    await startChallenge({ questId, expectedVersion })
  }}
/>
```

単体表示用デモなら渡される値は`{ questId: 'demo-harbor-clock', expectedVersion: 1 }`。通常起動では公開APIで取得した問題のID・版を使う。これは開始を依頼する入力であり、サーバーが作成した`Challenge`やクリア結果ではない。最新版・公開状態・認可の最終確認はA側APIが行う。公開GETと、最新mainの挑戦作成・撮影入口を接続済み。写真の送信・判定・保存へは進まない。

起動時の公開GET接続、読込中・ゼロ件・通信失敗の表示と再試行を実装済み。Viteの開発サーバーとビルド後のpreviewでは`/api`を`127.0.0.1:8787`へproxyする。サーバーは別ターミナルで明示デモとして起動する。本番配信環境のAPI転送設定は含まない。

地域選択は`GET /areas`の公開地域と`publishedCount`を表示し、`GET /quests?areaId=...`で絞り込む。全国は`areaId`を省略する。API依存ごとに一覧キャッシュを分け、地域変更・API差替時は古い地域の結果を表示せず、AbortSignalと結果タグの両方で遅い応答を抑止する。

```powershell
$env:QUEST_DATA_MODE='demo'; $env:NODE_ENV='development'; npm --prefix server run dev
```

デモAPIが停止中の場合は画面の再試行で復帰できる。問題一覧はcursorが返る間ページを読み込み、地域一覧も同様に検索する。地図は静的な全国地形プレビューのままで、固定マーカーはAPIモードで非表示。実地図との位置対応はない。
