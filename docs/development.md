# 共同開発・初期設定ガイド

最小Webアプリの起動と、4人で同じ土台を使う手順。React・TypeScript・Viteの共通画面と、設定時に使えるGoogleログインを用意した。開発用モードではローカルAPIから架空の1問を取得できる。Maps接続とクラウドの管理設定は別作業であり、このガイドの手順では変更しない。

## 1. 全員が同じ手順で起動する

### 1-1. リポジトリを取得する

リポジトリはチームで共有するコードの置き場所、ブランチは変更を分けて試す作業場所。初めて取得する場合は次を実行する。

```sh
git clone https://github.com/Devfest-Hackathon-2026/df-2026-t067.git
cd df-2026-t067
```

既に取得している人は、その`df-2026-t067`フォルダを開く。親の`hackason`フォルダでは実行しない。

既存の作業場所を更新する場合は、未保存の変更がないことを確認してからmainを取得する。他の人の変更を上書きしない。

```sh
git status
git fetch origin
git switch main
git pull --ff-only
```

資料PR #1、WebアプリPR #3、共通API PR #4、Firebase認証PR #5、旅行者UI PR #6、ローカルAPI PR #7はmainへ取り込み済み。未マージの変更を試す場合は対象PRのブランチを使い、勝手にマージしない。新しい作業は最新mainからブランチを作る。

### 1-2. Nodeとnpmを確認する

Nodeは開発ツールの実行環境、npmは必要な部品を揃える道具。共通の検証版はNode **26.7.0** / npm **11.19.0**。確認する。

```sh
node --version
npm --version
```

Nodeは[公式サイト](https://nodejs.org/en/download)から指定版を入れる。既にnvmを使っている人は`nvm install` → `nvm use`で`.nvmrc`の指定版を選べる。npmが異なる場合は、指定のNodeを選んだ後に`npm install --global npm@11.19.0`を行う。

`.npmrc`は異なる版でのインストールを止める設定。`EBADENGINE`になったら`--force`で進めず、上の2つの版とターミナルを開き直した結果を確認する。

### 1-3. 起動・確認する

`package.json`があるフォルダで実行する。初回の`npm ci`にはインターネット接続が必要。

```sh
npm ci
npm run dev
```

[http://localhost:5173/](http://localhost:5173/)を開く。既定モードでは地図のプレビューと架空の問題が表示され、問題を開閉できれば起動確認は完了。Firebase未設定時は「ログイン準備中」と表示し、ログインのボタンは無効。設定する場合は[認証ガイド](firebase-auth.md)に従い、localhostで確認する。終了は **Ctrl+C**。

画面からAPIを試す場合は、[ローカルAPI接続手順](local-api.md)に従い、明示した`local-api`モードと別ターミナルのAPIを起動する。設定なしの起動を実API接続成功と扱わない。サーバーの変更時は`npm --prefix server run check`も実行する。

匿名閲覧には環境変数やクラウドCLIは不要。Googleログインを使う場合だけ`.env.example`を`.env.local`へコピーし、6項目を入力する。実設定と元のJSONをGitへ含めない。`VITE_`で始まる値はブラウザへ公開されるため、秘密鍵やAI認証情報を入れない。[Vite公式説明](https://vite.dev/guide/env-and-mode)

変更したら、次で一括確認する。

```sh
npm run check
```

| コマンド | 内容 |
|---|---|
| `npm run dev` | 編集しながら画面を確認する |
| `npm run typecheck` | TypeScriptの型の誤りを検出する |
| `npm run lint` | Oxlintでコードの問題を検出する |
| `npm test` | 未接続の匿名閲覧・問題開閉・キーボード操作を確認する |
| `npm run test:watch` | テストを起動し、編集時に再実行する |
| `npm run build` | 配信用ファイルをローカルの`dist/`に作る。公開はしない |
| `npm run preview` | ビルド後の画面を[127.0.0.1:4173](http://127.0.0.1:4173/)で確認する |

5173番や4173番が使用中の場合は、先に起動した自分のサーバーをCtrl+Cで止める。別のポートへ黙って変えず、エラーとして表示する。サーバーは自分のPCだけで開く設定で、スマートフォン実機からの接続は次の検証にする。

他の人の変更を取得して`package-lock.json`が変わった場合も`npm ci`を行う。依存を変更する担当者だけが`npm install`を使い、`package.json`と`package-lock.json`を同じPRに入れる。`node_modules/`と`dist/`はコミットしない。

`fsevents`・`@firebase/util`・`protobufjs`の追加インストールスクリプトは実行しない設定にしている。この状態で起動・検証を確認済み。依存を追加してスクリプトの確認が出た場合は、共通基盤の担当者が確認する。[npm公式説明](https://docs.npmjs.com/cli/v11/commands/npm-install-scripts/)

### 1-4. 編集する場所と次の作業

| 場所 | 役割 |
|---|---|
| `src/main.tsx` | ブラウザにReactを表示する入口 |
| `src/App.tsx` / `src/App.css` | 日本語の起動画面とレイアウト |
| `src/features/quests/demoQuest.ts` | 架空の表示用サンプル。実APIの共通型ではない |
| `src/App.test.tsx` / `src/test/setup.ts` | 画面操作と、通信・端末権限を要求しないことの検証 |
| `vite.config.ts` | ローカルサーバー・テスト設定 |

最初に全員がこの土台を起動してから担当を宣言し、画面ごとに小さなブランチを作る。別々のアプリ一式を生成しない。共通型・API・認証は、[契約案](api.md)と照合して担当者に変更範囲を伝えてから追加する。

次は全国地図→問題→Googleログイン後に元の問題へ戻る導線、続けてカメラ/GPSと実AI照合を小さく検証し、1問の本人記録保存まで接続する。今回の土台にこれらの成功処理は含まれない。

## 2. 4人の役割案

**Aは共通基盤とサーバー、Bは謎を探す画面、Cは撮影と記録の画面、Dは自治体が出題する画面を担当する案。** ここでのA〜Dは開発メンバーの区分であり、アプリの利用者権限とは別。Aの担当者は決定して着手済み（氏名・GitHub名は未記入）。B〜Dの実メンバーへの割当はチームで決める。

### 2-1. 誰が何を作るか

画面IDは[画面一覧](screens.md)、データ名は[API設計案](api.md)を参照する。

| 担当（実メンバー） | 主担当の範囲 | 作って渡すもの |
|---|---|---|
| A：基盤・サーバー（担当決定・氏名未記入） | 共通の起動環境・型・API、Google認証とログイン画面T03、サーバーの権限確認・GPS/写真判定・保存・AI処理、各画面との接続調整 | 共通型と結果コード、ログイン後に元の問題へ戻る処理、B〜Dが呼ぶAPIと接続手順 |
| B：地図・問題（未定） | 全国地図T01、問題詳細・ヒントT02、挑戦を始める入口 | 地図から1問選んでヒントを読める画面、A/Cへ引き渡す問題IDと版 |
| C：撮影・本人記録（未定） | 撮影・写真確認・結果T04〜T06、本人の記録一覧・詳細T07/T08 | カメラ/GPSの許可・拒否・再試行、回答を送る画面、APIの判定結果と保存済み記録を表示する画面 |
| D：自治体画面・実地確認（未定） | 自治体向け画面A01〜A07、確認済み素材の整理、実地試験の段取りと結果の記録 | 素材登録→生成依頼→編集→試験→公開・休止の操作画面、撮影条件と実地試験の結果 |

例えば、Cは写真を送って結果を表示し、Aはサーバーで正解判定と保存を行う。DはAI生成を依頼する画面を作り、AはサーバーからAIを呼ぶ。DのA01はログインと所属確認の画面を担当し、共通認証と権限確認の処理はAと接続する。

### 2-2. 各担当が最初に進める小さな作業

全員が共通の土台を起動し、担当を共有してから着手する。次の表は着手順の案。画面は架空データで先に作れるが、実APIの接続前に共通の型と結果コードを合わせる。仮データの表示と実認証・実判定・実保存の成功は区別する。

| 担当 | 最初の作業 | その作業の完了目安 |
|---|---|---|
| A | 共通の起動手順を整え、1問分の型・API・結果コードとログイン後の戻り先をB〜Dと確認する | 全員が同じ土台を起動でき、画面側が使う入力・返却値と接続前の仮データの扱いが共有されている |
| B | 架空の1問を選び、問題文・ヒントから「挑戦する」へ進む画面を作る | 問題IDと版を保持してAのログイン処理またはCの撮影画面へ渡せる |
| C | 撮影→写真確認→結果表示の画面を作り、許可拒否・撮り直しの戻り道を用意する | 写真と撮影時の位置情報をAPIへ渡す箇所、結果コードごとの表示を確認できる |
| D | 架空の素材で登録・下書き編集・プレビューの画面を作る | 登録する情報と公開前の確認項目がわかり、Aへ渡すデータを説明できる |

### 2-3. 担当間の受け渡しと相談先

| 受け渡し | 先に合わせるもの |
|---|---|
| A ↔ B | 地図・問題用の`PublicArea`/`PublicQuest`、読込中・空・取得失敗の表示。公開データに正解座標・照合画像を含めない |
| B → A → C | 選んだ問題ID・版を保持し、未ログインならT03を経由してT04へ。ログイン取消・失敗時はT02へ戻す |
| C ↔ A | 写真と`CaptureMetadata`の送信、`AttemptResult`の結果コード、保存済みの`Discovery`の取得。クリア確定・日時・本人以外のアクセス拒否はサーバーで行う |
| D ↔ A | `ManagedQuest`、所属・権限、AI生成・試験・公開・休止API、公開する版。Dの試験操作では旅行者の記録を作らない |
| 全員 ↔ A | 共通型・依存ロック・認証・API・権限を変更する前に、変更範囲と影響する画面を共有する |

各実装者が自分の変更を検証し、別の1人がPRを確認する。Aは接続の調整窓口であり、全員分の実装・テストを一人で引き受ける役割にはしない。Dは実地試験を段取りし、B/C/Aも自分の担当機能の確認と不具合対応に参加する。課金・クラウド設定・本番公開の承認者は、この役割表とは別に[未決事項O-01/O-06/O-07](decisions.md)で確認する。

### 2-4. チームで決めること

1. Aの担当者名を記入し、B〜Dに実メンバーの名前またはGitHubユーザー名を割り当て、この共通表を更新する。
2. 各自の最初のタスクをIssueにし、「触る場所・成果物・受け入れ条件・担当」を書く。Aの作業量に偏りがあれば、チームで範囲を調整して表へ反映する。
3. 各担当が自分の作業と受け渡し先を説明できるか確認する。未決定の割当や境界は[Issue #2](https://github.com/Devfest-Hackathon-2026/df-2026-t067/issues/2)で相談する。

この表は役割を具体化した提案。担当者名の記入、B〜Dの割当とチーム確認は継続中のため、O-07とIssue #2で引き続き扱う。

## 3. GitとCodex

短いブランチを使う。例は`docs/...`、`feat/map-home`、`feat/photo-answer`。main直pushやforce push、他人の未保存変更の破棄をしない。競合は変更意図を確認して解決する。

Issueまたはチーム内連絡には「目的、変更する場所、受け入れ条件、担当」を書く。PRは「変更、確認手順、実行結果、未検証、仕様変更」を短く記す。Draft PRで途中の相談をしてよいが、モックを完成扱いしない。

Codexに最初に渡す指示の例：

> AGENTS.mdと最新のdocsを読み、今回の担当範囲だけを実装してください。作業前に既存差分と共通型を確認し、実装したテスト・型検査・buildの結果と、実機や実APIで未検証の点を分けて報告してください。課金・IAM・本番公開・仕様の拡大は独断で行わないでください。

CodexはAGENTS.mdを参照するため共通ルールをリポジトリに置く。ただしそれだけで人のレビューやサービス側の認可を代替しない。[S1](sources.md)

## 4. クラウド設定の順序（人間の承認が必要）

| 順番 | やること | 止める条件・確認 |
|---|---|---|
| 1 | クレジット・請求先・責任者・予算を確認 | 適用サービスが不明のまま無料を前提にしない |
| 2 | 共有のGoogle CloudプロジェクトとFirebaseの関係を確認 | 重複作成せず、チームに必要最小限の権限 |
| 3 | Google認証とWeb設定、許可ドメインを設定 | 本番・開発ドメインを明示。招待された自治体権限は別管理 |
| 4 | Maps JavaScript APIと制限付きキーを設定 | ドメイン/API制限。Places等は必要になるまで追加しない |
| 5 | DB・Storage・Functionsのリージョンと課金を承認 | 公開読み書きのtest modeは使わない。StorageのBlaze要件を確認 |
| 6 | Google Cloud側のGeminiをサーバーで試す | プロジェクト・モデル・認証・対象クレジットを実確認 |
| 7 | 呼び出し制限、予算通知、停止手順を試す | アラートだけで課金が止まるとは考えない |
| 8 | HTTPS上の実機で1問を確認し、限定公開 | 保存・削除・権利・役割を確認してから一般公開 |

Google認証設定は[S2](sources.md)、Storageの課金条件は[S9](sources.md)、Mapsのキー制限は[S7](sources.md)、予算通知は[S8](sources.md)を確認する。クレジットの金額や引換コードはこのリポジトリへ書かない。

ブラウザ用Maps/Firebase設定は利用者の端末から見える前提で保護する。秘密のAI資格情報やサービスアカウント鍵を`VITE_`変数へ入れない。`.env.example`には値でなく説明とダミーを置く。

## 5. 現在の検証と、実装後の検証

この土台の`npm run check`はローカルの型・静的検査・画面テスト・ビルドを対象にする。Google認証のブラウザ側の確認範囲は[認証ガイド](firebase-auth.md)、開発用APIの確認範囲は[接続手順](local-api.md)を参照する。Maps・GPS・カメラ・AI・保存の実接続と実機は未検証。GitHub Actionsが使えないため、ローカルの検証結果と別メンバーの確認をPRへ残す。GitHub Pagesへの公開設定も作らない。

最初の実機目標は1問を写真回答して本人の記録に残せること。続けて[受け入れ条件](acceptance.md)で境界・権限・二重送信・休止・障害を確認する。GPSや画像判定の技術検証を画面完成後まで先延ばしにしない。

デモには架空・利用条件を確認した素材だけをコミットする。実際の正解素材は非公開ストレージで別管理する。実機がなく試せない項目は未検証に残す。

## 6. 最初に渡してほしい材料

実地確認できる1〜3スポット、参考と別角度の写真、似た別対象、確認済みの紹介情報・撮影場所、費用を管理する人、実機の担当。これらが未整備でも画面・型・モックの作業は進められる。

正式名称、ロゴ、全国全地域の登録、高度な推薦は先に決めなくてよい。目的から離れる追加機能より、一周が動くことを優先する。
